# 大数据交互性能修复（2026-11-05）

## 范围与限制

目标是在不改变统计、筛选或图表独立配置语义的情况下，减少数据量增加后的界面停顿。
用户指定的 5230 服务可以访问，但当前浏览器连接工具两次在启动时失败（无法写入 kernel assets），未能连接其已有标签页、读取已加载数据或重放该数据。未使用用户私有数据，不能宣称原始现场已验证修复。

用独立 Chromium 导入生成的通用 CSV 复现：100,000 行，10,000 个 Account，20 个 Group，12 个 Period，Amount 求和。自动推荐产生 10,001 行 × 13 列的透视结果。此数据只验证通用机制，不定义产品业务结构。

## 证据与修改

浏览器 CPU 采样显示接收 worker 结果、表格全列极值扫描和图表渲染占用主线程。原实现虽缓存后台计算结果，但每次图表变更仍完整克隆传输表格，导致表格结果引用改变和派生扫描失效。

- Worker 为表格结果标记版本。仅当主线程确认持有同一版本时，图表更新才省略完整表格；数据、配置变化或缓存未确认时仍发送完整结果。
- 主线程保留未变化的表格对象，独立更新图表结果；下钻使用当前请求代次。
- 表格列极值扫描移到后台，每次表格计算只做一次。
- 稀疏表中完全等价的无记录单元格共享对象；保留全部单元格、样本说明、空值原因及百分比信息，不裁剪结果或改变算法。

## 浏览器对照

同一机器、同一 Chromium、同一生成数据、1440×1000、开发模式；等待结果提交后的两帧。原版本通过隔离的本地服务加载基线提交 3afb71c 的相关源码，不覆盖用户页面。以下为单次观测，不能作为所有数据的性能保证。

| 操作 | 修改前 | 修改后 | 操作期间最长主线程任务：前 → 后 |
|---|---:|---:|---:|
| 切换均值 | 3871 ms | 3700 ms | 651 → 416 ms |
| 切换求和 | 3590 ms | 3586 ms | 620 → 442 ms |
| 切换折线图 | 2133 ms | 608 ms | 622 → 241 ms |
| 切换柱图 | 2733 ms | 1111 ms | 857 → 462 ms |

图表切换受益明显；统计方式变更的总耗时没有明显改善，仍有主线程长任务，不能称为全面解决。求和保持 4,950,000，均值保持 49.5；图表变更不再传输整表。

- 新回归测试修改前失败，修改后通过；覆盖版本确认、错误缓存版本、数据替换、筛选失效、当前代次下钻。
- 稀疏结果与原计算引擎逐单元格深比较通过：普通值、总计百分比、行百分比、环比差。
- 全部 153 项逻辑测试通过，生产构建通过。
- Chromium：360 / 768 / 1440 三种视口的图表独立配置及共享筛选共 6 项通过，包括空结果、下钻、保存重开与现有无障碍断言。
- 现有 100k 聚合/拖放/撤销重做验收及 CSV/XLSX/PNG/SVG 导出验收 2 项通过。低分组数量的 100k 聚合更新为 503–654 ms（该验收与对照测量分别运行）。
- 未执行本轮 WebKit 回归；未完成用户原始标签页数据复测；没有真实用户研究。

可复跑：本地服务启动后执行 `node scripts/benchmark-pivot-browser.mjs`。可用 PIVOT_BENCH_URL 和 PIVOT_BENCH_ROWS 指定测试服务与生成行数，使用独立浏览器且不接触已有标签页。原始测量、CPU profile 和浏览器报告保存在忽略目录 `artifacts/performance-2026-11-05/`，不随代码发布。

## 剩余方向

高分组数量下的统计变更仍需要整表计算、传输和渲染。下一轮最值得处理的是完整结果的分块/按可见窗口传输，同时保留后台完整结果供复制、导出和下钻使用；需要先用用户实际已加载数据确认瓶颈及规模，再确定协议和验收预算。
